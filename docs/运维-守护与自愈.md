# 运维：守护与自愈

两台机器上的两类事故都指向同一件事：**ARTEX 的"进程还活着"不等于"服务可用"**。
这份文档记录症状、根因和已经加上的兜底。

## 症状：页面只剩「无法连接到后端服务」

登录页那句提示来自 `web/src/app/(auth)/login/page.tsx` 的 `.catch()`——登录接口
**任何**失败都会显示它，包括后端查库超时和数据库崩溃。所以这句话不能当作
"后端进程挂了"的证据。

排查顺序：

```bash
curl -s http://127.0.0.1:8787/api/health       # 不查库；200 只说明 HTTP 还能接
systemctl status artex --no-pager | grep -E 'Tasks|Memory:'
CG=$(systemctl show -p ControlGroup --value artex)
wc -l < "/sys/fs/cgroup$CG/cgroup.procs"       # 进程数：正常 30 以内
free -m | head -2                              # swap 打满=已经在抖动
docker exec artex-postgres-1 psql -U artex -d artex -tAc "select 1"
```

`/api/health` 返回 200 但登录失败，问题一定在数据库或数据库连接上；
`Tasks` 几百、swap 打满、cgroup 进程数几百，问题在子进程泄漏。

## 事故一：LLM 记录把数据盘写满（0.4.4 修）

每次 LLM 调用都把整段 prompt 写进 `llm_records`（单条 130–215KB），外加一份几乎
重复的 `raw_request`。一个任务日 32k 行、45GB TOAST，把数据盘写满后 PostgreSQL
反复 `No space left on device` → 重初始化 → 再崩。

已经加上的约束：

| 设置 | 默认 | 作用 |
|---|---|---|
| `llm_record_max_body_kb` | 16 | 单条正文上限，超出截断并标注原长 |
| `llm_record_store_raw` | false | 是否额外存原始 HTTP 报文（与归一化正文重复） |
| `llm_records_retention_days` | 3 | 保留天数，0=永久；后台每 30 分钟清一次 |

清理之后必须 `VACUUM FULL` 才能把空间还给文件系统——只 DELETE 的话表会一直停在
高水位，这正是它能长到 45GB 的原因。后台任务在表 >1GB、磁盘够、距上次回收 >6 小时
时做一次 `VACUUM FULL`，并且 `lock_timeout=5s`，抢不到锁就跳过，不卡业务写入。

另外后端会盯数据盘水位：低于 15% 打告警、低于 8% 打严重告警（`journalctl -u artex`）。

## 事故二：MCP 子进程泄漏把内存吃光（0.4.5 修）

每个 agent run 都会为每个可见的 MCP 服务器起一个 stdio 子进程。浏览器 MCP 走
`npx @playwright/mcp`，进程树是 `npx → npm → node`，而原来的 `Close()` 只
`Kill()` 直接子进程——子进程被留下、被 init 收养，但仍留在 ARTEX 的 cgroup 里。

叠加两个放大因素就炸了：

1. `task_concurrency_enabled=false`（默认不限并发），23 个任务同时跑，
   每个任务 3 个 worker，每个 worker 各起一套 8 个 MCP 服务器；
2. LLM 配置返回 403，任务反复重试却永远不结束，谁都不释放。

结果是几百个进程、1.7G 打满 cgroup、3.9G swap 抖动，连 `/api/health` 都超时。

修法：

- `norma/mcp` 把 MCP 服务器放进**独立进程组**（`Setpgid`），`Close()` 时
  `kill(-pgid, SIGKILL)` 整组收掉，`npm`/`node` 一起走；
- `watchdog.sh` + systemd timer 每 2 分钟检查一次：健康检查连续失败 3 次、
  cgroup 进程数 >120、内存占用 ≥90% 三个条件任一命中就重启，不必等人发现。

## 部署守护

```bash
install -m 755 watchdog.sh /usr/local/bin/artex-watchdog.sh

cat > /etc/systemd/system/artex-watchdog.service <<'UNIT'
[Unit]
Description=ARTEX watchdog (restart when the backend stops responding)
After=artex.service

[Service]
Type=oneshot
ExecStart=/usr/local/bin/artex-watchdog.sh
UNIT

cat > /etc/systemd/system/artex-watchdog.timer <<'UNIT'
[Unit]
Description=Run the ARTEX watchdog every two minutes

[Timer]
OnBootSec=3min
OnUnitActiveSec=2min
AccuracySec=15s

[Install]
WantedBy=timers.target
UNIT

systemctl daemon-reload
systemctl enable --now artex-watchdog.timer
systemctl list-timers artex-watchdog.timer   # 确认下一次触发时间
journalctl -u artex-watchdog -n 20           # 每次跑完都留一行"正常/重启"日志
```

阈值可以用环境变量覆盖：`ARTEX_MAX_PROCS`、`ARTEX_MAX_HEALTH_FAILS`、
`ARTEX_MAX_MEM_RATIO`、`ARTEX_HEALTH_URL`。

## 小内存机器的并发设置

3.6G 内存跑「ARTEX + PostgreSQL + sing-box + 五六个 MCP 服务器」时，
**一定要打开任务并发上限**，否则任务一多就会同时起几十套 MCP：

```sql
insert into settings(key,value) values('task_concurrency_enabled','true')
  on conflict (key) do update set value=excluded.value;
insert into settings(key,value) values('task_concurrency_limit','1')
  on conflict (key) do update set value=excluded.value;
```

UI 里对应「设置 → 任务并发上限」。
